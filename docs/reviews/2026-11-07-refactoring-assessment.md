# 重构评估：哪些结构会让同类 bug 反复出现

评估基线：`669b6a3`，已包含本轮之前的扫描、缓存提交、watcher 与 CLI 一致性修复。参考 [原架构报告](2026-11-07-architecture-review.md)与 [10 月 24 日核验记录](2026-10-24-code-review-triage.md)。本文件是调查与候选方案，不是已采纳的架构决定，也不宣称完成重构。

## 结论

值得做一次有边界的重构。优先对象是技能生命周期的写入和恢复流程，其次是所有权模型，再其次是跨运行时行为与编辑器会话。大文件和层数不是主要判据；同一个约束是否需要多个调用方分别记住，才是主要判据。

上次的小修修正了已复现的行为，也消除了部分重复，但没有把所有写入入口约束到同一个结构中。继续只补入口，仍然会有漏接的可能。重构的收益应是减少可绕过的入口、重复决策和需要同时维护的状态，而不是增加目录或包装层。

## 复杂度集中在哪里

| 优先级 | 区域 | 复杂度来自什么 | 建议 |
| --- | --- | --- | --- |
| 1 | 技能归档、恢复、合并、导入与缓存协调 | 一次操作跨实体目录、agent 链接、manifest、lock、用户元数据、缓存；各自处理顺序、失败和回滚 | 第一轮重构目标，先以归档/恢复为试点 |
| 2 | 技能身份、所有权与实际路径 | 字符串 origin 加多个可空字段；调用方自行决定能力、解析根目录、兼容历史身份 | 与生命周期试点一起收敛内部解析与权限规则 |
| 3 | Rust 与 TypeScript 的本地协议执行 | 共享文件格式，独立实现扫描、身份、哈希、归档与恢复 | 先增加共同的行为用例；共用执行核心另做选型 |
| 4 | 编辑器会话与懒加载文件树 | 主文件/附属文件分属两套草稿生命周期；查询结果又复制进局部树，靠会话与请求编号同步 | 前端第一优先，按状态所有权整理，而不是只拆 JSX |
| 5 | 仓库发现与安装发现 | 两次仓库遍历、互相依赖的 SkillService/CliService、缓存与网络逻辑分散 | 小范围统一同语义的仓库候选发现；不统一所有扫描与复制 |

InstalledSkills 的筛选/选择链条确实长，但比上述跨状态、跨持久化流程更容易验证。它可以后置，不能仅以 useMemo 数量作为必须重构的证据。

## 1. 生命周期：最值得改的是写入边界

### 已核实的结构

- [归档](../../src-tauri/src/commands/skill.rs#L1632)和[恢复](../../src-tauri/src/commands/skill.rs#L1877)在 IPC 文件中直接编排文件移动、链接修改、多个存储及回滚闭包。
- [合并](../../src-tauri/src/services/skill.rs#L2346)是另一套流程：验证内容、复制、删除原目录、补链接、更新缓存、迁移元数据；并非复用归档的提交规则。
- [导入](../../src-tauri/src/commands/skill.rs#L555)又独立跟踪 created_links、updated_imports、renamed_imports 和恢复过程。
- [AppState](../../src-tauri/src/store.rs#L4)公开缓存、元数据及多种锁。调用方可以直接改缓存或元数据，不需要先拿到受约束的操作上下文。
- 进程间 lease、刷新 mutex、内存 RwLock 分别解决不同问题。上次已将 watcher 和更新刷新接到同一 mutex，但接口并未使其他入口的遗漏变成编译错误。
- 归档/恢复把缓存保存也放入业务失败回滚路径；[agent 注册](../../src-tauri/src/commands/agents.rs#L283)已有另一种处理：权威提交成功后，缓存或 watcher 失败记为 refresh_failed。这里存在两种提交结果模型，需要明确其适用边界。

这些是控制流和接口审查结论。旧回归测试已证明部分缓存与锁问题确实发生过；本次没有把每一处写入口都宣称为新 bug。

### 根因与候选结构

现在正确性依赖每个入口安排对六类副作用的顺序。把函数原样搬去 services，只改变所在文件，调用方仍然能绕过共同规则。

建议让一个技能写入模块拥有缓存/元数据写权限和对应协调规则；IPC 只做参数接收、调用操作和返回结果。缓存可以继续用来索引技能，修改文件前仍须通过统一解析核实实际路径与所有权。操作之间共享已验证的路径/链接/持久化原语，归档、恢复、合并仍保留显式流程；不引入通用事务 DSL、任意步骤执行器或全项目 IO 接口。

具体顺序：

1. 为归档/恢复建立可直接调用、无需 Tauri 窗口的操作入口，先保持已有顺序、错误及回滚语义；迁移测试，保证可观察行为不变。
2. 将缓存修改限制在所属模块内，让新入口不能直接拼 RwLock 和 save；用已有增量批量提交与刷新机制落实这一边界。不是把所有操作都改成全量扫描。
3. 明确“权威提交失败”和“提交成功但派生视图刷新失败”的区别，再决定是否推广 agent 注册已有的结果模型。该步骤改变失败行为，必须单独更新 OpenSpec 与相关接口，不能混进纯搬迁。
4. 试点稳定后，再把合并、导入等接入相同边界。若这只是新增转发包装而没有删掉重复决策，就不继续扩展。

### 不能假装已有的保障

[agent-lifecycle journal](../../src-tauri/src/persistence/agent_transaction.rs#L6)只覆盖 agents/imports/settings/metadata 等允许的文件快照，不包含任意技能目录移动、lock 或 archive manifest。不能把现有 journal 改名成“通用事务”，就声称归档/更新具备崩溃恢复。

持久化崩溃恢复是独立设计问题，10 月 24 日记录已经将其排队。若要做，必须定义每一步重启后的恢复结果、临时目录与链接归属、提交点及桌面/CLI 同步协议；遵守 ADR 1、3、4。现有租约和普通错误回滚不等于断电原子性。

## 2. 身份与所有权：把判断从每个入口收回

[InstalledSkill](../../src-tauri/src/services/skill.rs#L47)和缓存记录通过 origin 字符串、home_path、home_agent、plugin_source 等独立字段表示不同来源。单看类型不能判断哪些组合有效，也不能判断哪些操作允许执行。归档、删除、合并、内容写入因而重复做来源判断。

已经有 [ManagedSkill::resolve](../../src-tauri/src/services/skill.rs#L207)，负责路径边界和只读保护。应以它为起点补齐内部已解析目标，而不是再造第二个解析器：将已核实的 SSOT、agent 实体、外部导入、plugin 表达为内部带数据的分支，让每个分支携带必需信息；在操作入口决定能编辑、移动、删除源目录还是只移除引用。

磁盘与 IPC DTO 暂不变，避免为了内部类型整洁引入迁移。特别要保留“注销 agent 后的外部引用仍可沿用原 agent ID”的事实：不能从 ID 前缀推断所有权，不能把显示名、相对目录、真实路径和稳定 ID 重新合并成一个字符串。

这能防住的是新增来源时漏加某个入口的保护，不能替代真实文件系统的路径验证，也不能消除外部进程修改文件的时间窗口。

## 3. 双运行时：共同格式不等于共同算法

Rust 与 TypeScript 各自实现本地协议是事实。历史上哈希排序、archive ID 和当前一致性规则确实产生过偏差；共享 fixture 已经捕获并约束了一部分问题，不能说同步仅靠注释。

短期最有收益的是把共享 fixture 从文件读写扩展为共同场景：对同一份隔离文件树执行扫描、归档/恢复、历史元数据迁移，并断言身份、所有权、链接、标记和失败后的状态。允许平台路径、时间等非契约差异。已有双方行为测试与哈希向量应复用，不要求建立一个庞大的通用测试框架。

共用 schema 或生成类型可以减少字段漂移，但不会自动统一目录遍历、哈希排序和回滚。若要从根本上去掉算法双实现，候选是把本地操作提取为不依赖 Tauri 的 Rust 核心，桌面调用该核心，npm CLI 通过独立无界面可执行程序调用它。代价是跨平台二进制分发、进程协议、版本匹配及构建所有权；它不是本轮可以顺手完成的小重构，也尚未证明收益超过代价。

不建议让 CLI 必须连接正在运行的桌面应用，这会改变当前独立使用的能力。是否采用共用执行核心，应在前两项边界稳定后单独选型；此文不把它记为已采纳决定。

## 4. 前端：编辑器比大列表更需要按状态所有权整理

[useEditorState](../../src/lib/useEditorState.ts#L8)维护主文件草稿、dirty、保存时提交的版本和 session；[SkillContentPane](../../src/components/skills/SkillContentPane.tsx#L205)对附属文件再维护一套草稿/session/保存确认，并向父级上报未保存状态。两处都必须防止“旧保存清掉新草稿”，已有真实回归场景与测试。

文件树还有另一组同步：[查询取得 children 后复制进 nodes](../../src/components/skills/SkillContentPane.tsx#L365)，根查询更新时再合并已有 children。这里有查询缓存、局部树、加载状态/ref、session、navigation request 等多个协调对象。外部变更后已加载子目录能否及时更新，仍需专门复现；本次不将这条风险升级成已复现缺陷。

建议先拆清两个所有者：编辑会话集中维护按 skill ID 与文件路径定位的草稿和保存确认；文件树查询层持有各目录的服务端结果，UI 只保留展开目录、选中文件等交互状态。布局、分栏、翻译任务继续归各自现有职责，不全部塞进一个超大 hook。

提取 hook 的验收不是行数变少，而是主/附属文件不再各有一份保存确认算法，查询结果不再需要第二棵可写副本。既有 session 和版本保护在新结构验证前必须保留。

## 5. 仓库发现：有一处适合小范围合并

[CliService::scan_dir](../../src-tauri/src/services/cli.rs#L941)与 [SkillService::scan_for_skills](../../src-tauri/src/services/skill.rs#L1507)都遍历解压仓库并发现候选。可以共用候选发现结果，浏览负责展示元数据，安装负责选择与目标预检。SkillService 依赖 CliService 的 ZIP 能力，CliService 又依赖 SkillService 的根技能识别，也说明当前职责互相交叉。

本地扫描另有 SSOT/agent 身份、imports 优先权和悬空链接归属规则，不能直接用仓库扫描替换。先统一两个同语义的仓库候选发现，再考虑把 ZIP/下载职责放到合适模块；CliService 的重命名可随实际职责整理完成，单独改名不会减少算法数量。

| 安装复制与合并复制必须统一安全规则 | 实测安装跳过目录链接，合并拒绝目录链接并保留原文件。一个是将远程内容物化，一个必须确保本地原件无损，策略不同有必要。合并在复制前还通过有深度上限的哈希验证来源；仅从 copier 本身没写深度参数，不能推出可直接触发无限递归。并发变更窗口仍是独立问题。 |
| 仓库扫描与本地扫描是同一个算法的重复 | 两者输入和业务语义不同。更适合合并的是两条仓库候选发现路径。 |
| Result<_, String> 就说明结构化错误已丢失 | 部分 String 实际携带 CommandError JSON，前端会解析。应检查实际丢失身份/错误码的路径；例如从错误文案的冒号前猜技能名，比单纯返回类型更值得收敛。 |
| 状态分四处本身需要统一 | 不同资源的运行态、全局只读快照和文件写锁可以分开。优先收拢同一技能状态的写权限，而不是把凭证、翻译与所有锁塞进一个全局容器。 |
| 存在三套仍在运行的 CLI 血统 | Rust CliService 是历史命名；所引用的外部 CLI 不代表当前还有第三条执行路径。命名值得改进，不能当成三个活跃引擎。 |

## 首轮重构的验收条件

1. 归档/恢复操作可在临时 HOME 下直接测试，无需构造桌面窗口；先保持现有用户行为和协议不变。
2. 试点入口不能自行写缓存或拼来源保护。共享写入入口内部落实需要的锁与刷新，能力判断来自已解析目标。
3. 外部引用不能被移动/归档/删源文件，plugin 保持只读，用户链接归属仍符合 ADR 4；历史 ID 与元数据标记保持。
4. 扫描、移动、链接、每个权威存储及缓存保存的失败结果都有明确断言；若改变提交后刷新失败语义，要另有行为契约，不能以纯重构名义改变。
5. 同一物理技能经全量和增量路径得到一致记录；缓存失败与后续重建不会改变用户文件。
6. 旧路径与旧判断在替换后删除，不保留新旧两条可写主干。小试点应先稳定，再扩展到合并/导入；不同时改协议、执行引擎和前端编辑器。

不把“扫描不再发现任何 bug”作为验收。可检查的目标是同一规则只有一个权威实现、调用方难以绕过它、同一失败场景不再需要逐入口补丁。

- Rust 本地合并目录链接测试：1 项通过，调用生产 merge 操作并断言拒绝、原文件与链接保留。
- 前端 SkillContentPane、useEditorState、queryInvalidation：3 文件、23 项通过。
