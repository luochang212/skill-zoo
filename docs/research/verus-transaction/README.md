# Verus recovery feasibility study

Date: 2026-10-23. Related [ADR 3](../../../adr/implemented/3-keep-verus-optional-and-outside-production-builds.md).

## Outcome

**Continue isolation; do not add Verus to the production build or required CI.**
An executable recovery model verifies, and five deliberate implementation errors
fail verification without weakening its contracts. This demonstrates useful
reasoning about snapshot selection, partial replay and retries. It does not
formally verify Skill Zoo's production recovery implementation or filesystem.

The [second round](round2-production-recovery.md) adds production-path recovery
failure and retry tests for Rust and CLI using shared fixtures, plus a proof of
partial replay idempotence. Extracting a shared executable transition core would be a
separate design change: the small amount of pure logic currently lives among
storage operations, so extraction solely for Verus has not yet earned its cost.

## Reproduce

Use the official weekly release
[`0.2026.10.18.7d82994`](https://github.com/verus-lang/verus/releases/tag/release/0.2026.10.18.7d82994).
The experiment used macOS arm64 and Rust `1.99.1`:

```sh
rustup toolchain install 1.99.1 --profile minimal --no-self-update
python3 docs/research/verus-transaction/verify.py \
  --verus /absolute/path/to/verus \
  > /tmp/verus-recovery-results.json
```

Run from the Skill Zoo repository root. Download/extract the appropriate official
binary first; see [Verus installation](https://github.com/verus-lang/verus/blob/main/INSTALL.md).
The script uses only Python's standard library, runs each case in a temporary
directory, bounds verification time/resources, and returns failure for unexpected
results. It never edits the model or production files. No dependency, toolchain
override, build command or CI gate was added to this project.

For this session the binary lives under
`/tmp/skill-zoo-verus-study-20261023/verus-arm64-macos/verus`.
Rust `1.99.1` was installed in the local rustup store; the default remains
`stable`. The 451,327,093-byte release archive was downloaded into the same
temporary study directory and removed after extraction and checksum recording.
Other platforms were not exercised.

## What the model establishes

[`recovery.rs`](recovery.rs) models an ordered list of affected file slots.
`None` represents absence and `Some(u64)` is an opaque content token, not an
actual file hash. Before/after snapshots have matching slots, as generated by
the production `commit_with` loop. The model assumes the journal and commit
marker remain available and unchanged during recovery.

For arbitrary vector lengths and supplied token values, it establishes:

- A completed prefix contains exactly the selected snapshot; remaining slots
  keep their incoming values. The loop terminates and indices stay in bounds.
- `committed=false` selects before-state; `committed=true` selects after-state.
- Partial replay retains the logical journal. An arbitrary interrupted prefix
  followed by one complete retry produces the selected state and permits cleanup.
- Completing recovery twice preserves the same selected state.
- Repeating the same partial prefix preserves the partially recovered state and
  the correct journal-retention decision, while leaving the unwritten suffix alone.

| Production mechanism | Model correspondence | Unverified boundary |
| --- | --- | --- |
| `write_snapshots` in `agent_transaction.rs` | `apply_prefix` | Atomic write/delete behavior and mapping bytes to slots |
| `recover` chooses before/after using `journal.committed` | `recover_prefix` | Reading/parsing/validating the actual journal |
| `write_snapshots(...)?` precedes journal removal | `keep_journal` remains true for a partial prefix | Actual error propagation and removal behavior |
| A later lease acquisition calls recovery again | `interrupted_then_retry` | Process restart, exclusive lease and eventual IO success |
| Replaying the same snapshot again | `completed_recovery_is_idempotent` | Storage implementation and external modification |
| Repeating a failed replay prefix | `partial_recovery_is_idempotent` | Identical journal/marker across retries and actual IO behavior |

This is a hand-maintained correspondence, not a mechanically proved refinement
from production code to the model. The proof does not cover the full commit
protocol or creation/persistence of the committed marker. It also does not cover
manually authored journals whose before/after key sets differ.

## Storage assumptions and adoption cost

The model replaces each successful file operation with an indivisible slot
assignment. Failed or interrupted recovery completes a prefix, keeps the journal
intact, and can be retried with the same snapshots. There are no outside writers.
These are assumptions at the filesystem boundary, not proven guarantees.

In particular, the production writer syncs file contents before rename; this
study did not establish directory-entry persistence or ordering under power loss
on APFS/NTFS/Linux filesystems. No claim about those platforms follows from the
vector proof. Path validation, symlinks, permissions, invalid JSON, disk-full
handling, cross-process exclusivity and TypeScript CLI correctness remain outside
the Verus proof. The earlier hash-to-rename race also requires a separate model.

The [current support table](https://verus-lang.github.io/verus/guide/features.html)
still lists direct IO and async/await as unsupported. Modeling/wrapping those
operations adds a trusted boundary; [assumptions](https://verus-lang.github.io/verus/guide/tcb.html)
must not be mistaken for verification of their implementation.

Verifier execution is cheap for this example (about 2.3 seconds for all six runs).
The significant costs are tool setup, correct specifications, storage modeling
and keeping the model aligned with production Rust and the separate CLI. Existing
tests already exercise snapshot selection and recovery outcomes; this trial
found no new production defect. The additional benefit is the quantified argument for the
abstract replay algorithm, rather than newly demonstrated disk-level safety.
