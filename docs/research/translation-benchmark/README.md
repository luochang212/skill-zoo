# 翻译策略实测：DeepSeek Flash

2026-11-04，生产实现固定于 `fb397fe`。本次只增加研究材料，没有改变应用、模型配置或凭据。

结论：优先对 DeepSeek 翻译显式关闭思考；不要用“原文加 prompt”替代所有确定性保护。并行适合缩短长文总耗时，不能指望它带来同等幅度的首次显示改善。当前保护器要求所有标记按原顺序出现，会把合理的中文语序调整判为失败，应该将这种失败与标记改写区分。

## 方法与边界

- 从已有 Claude Code 设置中在内存读取 DeepSeek 凭据，直接请求官方 `https://api.deepseek.com/chat/completions`，模型 `deepseek-flash`。应用配置同样使用此模型和协议。没有修改配置，也没有把凭据存入脚本、参数、报告或响应记录。
- 4 篇固定英文 Markdown：605 字节短文、1,773 字节真实技能、6,913 字节长技能、6,483 字节代码密集文档。后两篇分别覆盖长正文和大段重复但不同的代码。短文及代码文档同时含公式、路径、链接、frontmatter 和安全限定语。
- 每个正式组合重复两次。整篇试验串行执行；并行试验按 2,200 字符目标装箱完整段落，保持 frontmatter 和围栏代码完整，限制为 2 或 3 路。长文形成 5 块，代码文档形成 4 块。
- 所有请求流式返回；显式设置 `thinking.type`。未设置 reasoning effort，启用思考时采用服务商默认。普通请求输出预算为 8,192 token；成功完成的长文思考补测预算为 32,768。两轮补测均正常结束，预算没有触顶。应用现有预算更高，因此 8,192 上限试验不能代表应用必然截断。
- Rust bridge 通过 `include!` 编译真实 `src-tauri/src/services/translation.rs`，复用保护、还原、定向修复提示、片段规划与拼接。只桩替换未使用的模型配置类型，不复制保护算法。
- 记录官方 usage，包括缓存输入和思考输出；总 token 为所有请求的输入加输出，修复计入。缓存命中降低费用，不从总 token 中扣除。
- 表中时间为两次算术均值。首次正文为首个非空 content delta；“可读代理”为累计至少 20 个中文字的时刻，并行取第一块。它不是渲染器实测，也可能含 frontmatter description，不能当作精确的应用首段显示时间。局部 JSON 方法取首个完整可解析字符串，而不是 JSON 前缀；该实验原型最终提交仍等全文完成。
- 保真校验检查受保护片段、非 description frontmatter 字段及公式；另区分字节差异与忽略片段末尾空白后的内容差异。这不是完整的语义质量评估，不能证明无漏译或所有措辞均正确。人工抽查确认了标记重排和行内代码被翻译的具体案例。
- 两次重复不足以建立尾延迟、长期失败率或并发最优值。本次只测英译简中、一个模型、一个网络环境。请求的缓存命中和当时负载不同，约零点几秒的差距不应解读为稳定优势。

## 正式结果

### 关闭思考

保持当前保护策略。token 含输入、正文输出、思考输出及必要修复。

| 文档 | 模式 | 可读代理秒 | 总耗时秒 | 总 token | 完成并保真 |
|---|---|---:|---:|---:|---:|
| 短文 | 开启思考 | 7.725 | 8.154 | 1,877.5 | 2/2 |
| 短文 | 关闭思考 | 1.058 | 1.513 | 408 | 2/2 |
| 长文 | 开启思考，32,768 预算 | 41.122 | 47.215 | 12,717.5 | 2/2 |
| 长文 | 关闭思考 | 0.905 | 8.824 | 3,301 | 2/2 |

长文首次正文 delta 的均值从 40.991 秒降至 0.712 秒。关闭思考后，总 token 减少约 74%，总耗时减少约 81%。短文总 token 减少约 78%。这些是样本结果，不是对所有请求的承诺。

另有两次 8,192 预算的思考长文试验：平均 36.997 秒触及上限，总 token 9,900，均未产生正文。正式记录不对此自动修复；生产流在截断时也应失败而不是修复。

### 分块并行

全部关闭思考。先比较保留当前保护策略的长文。

| 长文策略 | 可读代理秒 | 总耗时秒 | 总 token | 完成并保真 |
|---|---:|---:|---:|---:|
| 整篇 | 0.905 | 8.824 | 3,301 | 2/2 |
| 2 路并行，5 块 | 0.726 | 5.885 | 3,709.5 | 2/2 |
| 3 路并行，5 块 | 0.762 | 4.590 | 3,725.5 | 2/2 |

2 路和 3 路总耗时分别下降约 33% 和 48%，token 增加约 12% 和 13%。首段的绝对差异不到 0.2 秒，不能靠两次重复证明稳定改善。

代码文档的 2 路试验均触发一块修复，平均 5.157 秒、1,700.5 token，比整篇的 2.732 秒、972.5 token 更差；3 路没有修复，平均 1.964 秒、1,195.5 token。不能因此断言 3 路比 2 路更可靠：重试与随机性干扰了这一小样本。

原文不保护的 2 路并行也已测试：长文 5.886 秒、3,203.5 token；代码文档 4.885 秒、4,696.5 token。并行没有消除复制代码的 token 开销。

### 保护方式

- `protected`：真实生产保护与最多一轮定向修复。
- `raw`：整篇原文加保留规则，不用占位符。
- `local`：围栏代码留本地；其余 Markdown 字符串组成一个 JSON 数组输入；返回 `{"translations":[...]}`，开启 JSON object mode；每个字符串仍用生产保护器保护行内内容与 frontmatter。
- `local_plain`：相同本地围栏代码与 JSON 方式，但正文不使用行内占位符，只通过 prompt 要求保留。

| 文档 | 策略 | 可读代理秒 | 总耗时秒 | 总 token | 严格保真通过 |
|---|---|---:|---:|---:|---:|
| 短文 | protected | 1.058 | 1.513 | 408 | 2/2 |
| 短文 | raw | 1.073 | 1.497 | 359.5 | 2/2 |
| 短文 | local | 1.304 | 1.334 | 486.5 | 2/2 |
| 短文 | local_plain | 1.334 | 1.352 | 454 | 2/2 |
| 中篇 | protected | 1.004 | 4.041 | 1,320 | 0/2 |
| 中篇 | raw | 0.753 | 2.502 | 819.5 | 2/2 |
| 中篇 | local | 2.842 | 2.869 | 1,122.5 | 0/2 |
| 中篇 | local_plain | 2.712 | 2.722 | 914.5 | 2/2 |
| 长文 | protected | 0.905 | 8.824 | 3,301 | 2/2 |
| 长文 | raw | 0.737 | 7.820 | 2,898.5 | 1/2 |
| 长文 | local | 8.608 | 8.648 | 3,447 | 1/2 |
| 长文 | local_plain | 8.217 | 8.249 | 3,101.5 | 2/2 |
| 代码密集 | protected | 1.024 | 2.732 | 972.5 | 2/2 |
| 代码密集 | raw | 0.887 | 6.878 | 4,482 | 0/2* |
| 代码密集 | local | 1.605 | 2.034 | 846.5 | 2/2 |
| 代码密集 | local_plain | 1.612 | 1.991 | 786.5 | 2/2 |

\* 代码文档的 raw 两次严格失败均仅涉及末尾围栏代码块后的换行，不是代码内容损坏；忽略片段末尾空白后两次均保留内容。相同差异也出现在原文并行方法。这里保留严格失败记录，同时不把它描述成代码被修改。

整篇原文在短文中比当前标记策略少约 12% token；长文少约 12%，但有一次把行内代码 `Q1 - <title>` 翻译成 `Q1 - <标题>`。提示词规则不能替代确定性保护。

代码密集文档中，本地保留代码、不用行内标记的候选方法，相比整篇原文减少约 82% token、总耗时减少约 71%。不过整篇 JSON 在长文里必须等首个很长的字符串结束才能解析，首块约 8.2 秒才可用，明显不适合直接作为应用的流式显示方案。这证明本地保留大段代码的价值，没有证明整篇 JSON 是最佳协议。

### 已复现的保护协议问题

中篇的两次生产保护试验里，每个 SZP 标记都原样出现且恰好一次；失败原因是标记顺序变化。原文先写 Verification、Trade-offs，最后写“under Consequences”；中文自然写成“在 Consequences 下……Verification……Trade-offs”。生产还原器因要求全局顺序一致而拒绝，定向修复两次也未成功。

`order-repro.json` 给出了无需 API 的最小复现，直接调用生产代码，确认全标记完整但 restore 失败。修复计划只取部分受影响区域，不能保证修正这种跨标记语序变化。

建议区分行内内容和块级结构：行内保护应允许符合句法的重排，同时验证标记唯一且完整；块级代码及 frontmatter 继续确定性保留并检查结构位置。不能简单取消所有顺序检查，也不能把这次判断扩展为任意移动代码块都安全。

## 建议的实施顺序

1. 对已确认支持的 DeepSeek 翻译请求显式关闭思考，保持流式输出。不要把服务商私有字段盲目发给所有兼容接口；思考策略改变时应更新翻译缓存策略身份，避免旧结果掩盖效果。
2. 单独修复行内标记顺序过严的问题，保留代码、链接和非翻译 frontmatter 的确定性保护；不要继续堆叠修复轮次来绕过它。
3. 再对长正文引入语义分块和有限并发，优先首块，保持展示顺序。2 或 3 路是待扩大样本验证的候选，尚无通用最优值。
4. 代码密集文档探索“本地保留代码块＋按语义块翻译并流式提交”，避免模型输出大段代码，也避免整篇 JSON 的首段阻塞。当前实验尚未实现这个组合，不能声称其性能已经验证。
5. 等待首段期间保留原文可消除整页空转，但不降低真实译文延迟；该交互需更新当前明确要求转圈的 OpenSpec，不能用显示原文伪装首次译文时间。

## 记录、费用与试跑勘误

最终 50 次正式试验，每组两次。原始记录保留全部 76 次试验、126 次 API 请求（含并行子请求、定向修复和协议试跑）。总输入 80,358、输出 129,761，合计 210,119 token；输入中缓存命中 34,028、未命中 46,330。

按测试时官方 Flash 非高峰价格估算，全部请求约 **$0.085**；不是实际账单。思考已计入输出，不重复累加。价格来源：[Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)。非思考开关来源：[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。

试跑原始数据没有删除，汇总选择规则在 `summarize.py`：

- v1 的 local 使用提示词要求返回 JSON 数组，但继承了“只返回 Markdown”的相互冲突约束；不纳入最终 local 比较。
- v2 去掉冲突，但仅靠 prompt 的数组仍出现不按格式返回或无效 JSON。v3 改为官方 JSON object mode 和明确对象协议，最终 local/local_plain 只选 v3。没有因此宣称模式能保证元素数量、顺序或翻译质量。
- v1 的低预算思考长文被测试脚本错误地在截断后发起修复。生产流会拒绝截断结果；v2 重跑并禁止这种修复。v1 的额外开销只保留在试跑与全部费用中，不用于正式方法比较。
- 试跑初始自检发现生产保护/还原会规范化围栏周边换行，故改为检查保护内容确实往返，没有把整篇字节恒等当作已有保证。

## 复现

需要 Python 3、Rust，以及已构建的桌面 Rust 依赖（`src-tauri/target/debug/deps/`）。无需新增第三方依赖。脚本会从 `~/.claude/settings.json` 的 env 中读取 `DEEPSEEK_API_KEY`，缺少时使用 `ANTHROPIC_AUTH_TOKEN`；只发往固定官方域名。不会打印凭据或原始错误响应。

```sh
python3 docs/research/translation-benchmark/run.py
python3 docs/research/translation-benchmark/summarize.py
```

脚本根据现有 results 跳过已完成正式组合，重新执行不会自动重复付费请求。若需独立新一轮，先另存已有结果再运行。fixtures 为已冻结快照，不依赖其他人的本地技能安装。Rust bridge 仍会编译当前 checkout 的生产实现，复现前应核对 `metadata.json` 的 commit 与源码哈希。

- `metadata.json`：源码版本、参数和样本大小。
- `fixtures.json`：公开内容与合成用例快照，不含凭据。
- `results.jsonl`：全部原始译文、调用耗时、usage、修复与检查结果。
- `summary.json`：最终组合的均值与保真诊断，由脚本生成。
- `order-repro.json`：标记完整却因语序变化失败的离线最小复现。

未验证其他模型、其他语言、macOS WebView 的实际首帧、长期负载和尾延迟；没有修改生产代码，也没有运行与研究脚本无关的前后端全量测试。

## 后续实现复验

本次实现没有采用并发或整篇 JSON。新校验按源文行分组允许行内标记重排，保留跨组顺序与唯一性；支持的模型默认关闭思考。原始 50 组试验及对应版本未被重写。

`post-fix-checks.json` 单独记录：两份旧中篇失败的首轮响应现在均能直接还原；两次使用新提示词的 DeepSeek 非思考请求也均无需修复，首个正文片段约 1.47/0.87 秒，总耗时约 3.39/2.98 秒，各 1,073 token。这两次后续请求不计入前文原始 126 请求和费用汇总。单请求 SDK 的参数传递另有本地 wire test 验证，尚非所有服务商的线上验证。
