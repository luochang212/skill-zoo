# Design

## Decisions

1. **Filter server-side, not in the UI.** Removing `github_token`/`github_token_expires_at` from `get_settings` responses is the actual boundary: a UI-only change would leave the raw token one `invoke` away from any renderer code. The command stays generic otherwise. The filter is one pure helper over the values map so it is testable without `tauri::State` (repo test pattern).
2. **Status without the secret.** `get_github_credential_status` returns `{ hasToken: bool, expiresAt: Option<String> }` read from the same settings map. The row and dialog need exactly this (existence + expiry + verification results); nothing needs the token back.
3. **Replace-only: no removal affordance.** The product maintains exactly one credential. Saving a new token replaces the old one, and the UI offers no remove action at all (product-owner decision, revising the earlier two-step-remove draft of this change). Replace covers every practical transition: rotation, fixing a revoked token, moving machines. GitHub-side revocation is the real de-authentication, which means the app's copy becomes an inert string that expiry metadata or loud 401s surface; the only unreachable transition is "voluntarily downgrade to anonymous", which gives up a harmless capability rather than being locked out of one. The retired "clear the input and save" removal only made sense with prefill and would misfire on an empty-by-default input; with replace-only, the save button disabled on an empty draft is the only empty-submit guard needed.
4. **One status query.** `useGitHubCredentialStatus` replaces `useGitHubToken` + `useGitHubTokenExpiresAt`. The two hooks were same-shape queries each fetching the whole settings map to pick one field (two roundtrips, two invalidations). The save mutation's `onSuccess` sets status data (`hasToken`, `expiresAt` from verification) and invalidates once. `staleTime: 0` is kept because status must reflect the disk truth like the rest of the settings page.
5. **The saved credential is stood in for by a real mask value, guarded by an unchanged rule.** Draft is a three-state model: `null` = untouched (the input derives its value to the mask, so no fill effects are needed, late status loads included), any string = the replacement candidate; `onSuccess` returns the draft to `null` (mask). The glyph is the platform's actual password-mask glyph: WebKit on macOS renders password dots with the system font's private secure-dot glyph U+F79A (`RenderBlock::updateSecurityDiscCharacters`, WebKit commit 69d20a8; applies when the primary font is the system font, which the app's default Tailwind stack is), every other engine (Windows WebView2, Linux WebKitGTK) draws plain U+2022 bullets, and the mask uses the matching codepoint per platform. Verified empirically with Playwright WebKit: real mask and `\uF79A` run both measure 6.0px dots / 2.7px gaps at 14px (`•` is 2.7px, `●` is 11.0px). Because the mask is a real value, selection, deletion, undo, copy, and re-focus behave exactly like ordinary text. The clipboard only ever receives meaningless mask characters, so write-only holds even there. Guardrail (correctness): saving stays disabled while the draft contains mask characters, because untouched, partially cleared, and pasted-back are all "unchanged", so a submit can never send dots to GitHub, and a splice (typing or pasting into the middle of the mask) is visible but can never be submitted. No auto-selection (product-owner decision, removing the second guardrail drafted for this): focus places a caret and selection is entirely the user's. Select-all → delete → paste is the habit they described, and it is exactly how the old prefilled real-token field behaved. The placeholder is instructional copy ("输入新 Token 以替换"), visible only after the user clears the mask. Dots-as-placeholder was tried first and rejected: a placeholder is a hint, not content. It cannot be selected or deleted, which users read as a broken field.

6. **The dialog verifies the saved token on open.** The saved state alone could not show the current quota. The dialog's "save to verify its quota" copy invited a write just to see information, and a token revoked on GitHub stayed invisible until updates failed. Since opening the dialog is infrequent and `GET /rate_limit` does not count against the quota, a live check on open is essentially free. Write-only forces the shape: the renderer has no token to pass, so a new `verify_saved_github_token` command reads the credential server-side (lock → clone → drop the guard before awaiting, because a std MutexGuard is not Send) and reuses the same verification routine; only the result crosses the bridge. The result is a query (not the save mutation), enabled while the dialog is open with a saved token, `staleTime: 30s` as a reopen damper; a successful save seeds the query cache with its fresh verification so a quick reopen skips the refetch. Priority in the status line: fresh save → live check truth (beats stale persisted expiry metadata) → "verifying" → persisted-expired → configured fallback. A transport failure falls back to the saved-state line, because a passive check must not scream "verification failed". That copy stays reserved for the save flow.

## Trade-offs

- The dialog can no longer show "which token is this?" beyond state + expiry. For a fine-grained PAT with public read only, the expiry line is sufficient identification; storing a user-facing token label is speculative until asked for.
- `get_settings` consumers outside the token feature see two fewer keys. Frontend grep shows no other reader of the credential keys; the CLI reads the file directly and is unaffected.
- Replace-only has no in-app path back to anonymous. Accepted: anonymous is the app's fully functional initial state, and a user who wants the app to hold nothing revokes on GitHub's side, which neutralizes the stored copy.

## Verification boundary

Component tests cover dialog behavior against mocked `invoke` (mask stand-in on open, unchanged-guard, replace flow, absence of any removal affordance, settings read without credential keys). The mask glyph sizing and the rejected select-on-activation path (click caret placement collapses focus/mouseup selections in real WebKit) were verified with Playwright WebKit. The Rust side covers the pure helpers; the `tauri::command` wiring stays inspection-reviewed, consistent with the repo's existing test pattern.
