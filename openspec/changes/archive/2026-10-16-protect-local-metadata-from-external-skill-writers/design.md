# Design

## Context

共享锁 v3 是三方共写面（本方 / npx skills / gh skill）。两轮评审（[evidence/](evidence/)，含对上游真实锁函数与 vercel 发布包的运行时探针）确立的事实基础：

| 事实 | 证据等级 |
|---|---|
| gh 写锁 = 整文件读改写；无关条目的 `ref`/`commitSha` 被剥，`skillFolderHash` 等已声明字段无损保留；同名条目整体重建（仅继承旧 `installedAt`） | 实测（Go 探针 × 真实 `RecordInstall`） |
| vercel 1.5.3/1.7.2：无关条目整表往返保留未知字段；同名重建丢弃未传入字段 | 实测（发布包函数探针 × 2 版本） |
| gh v2.102.0 不消费 `skillFolderHash` 做决策（更新读 frontmatter `github-tree-sha`）；vercel 消费它（40 位 hex 按 git tree hash 比较） | 源码 |
| `RecordInstall` 实参 = `discovery.Skill.TreeSHA`（子树 tree SHA），与本方 `commitSha` 值域语义相同 | 源码 |
| 本方安装允许「树查询失败 → 无基线」的降级（安装链注释明示）；检查不回写基线（E1 修订） | 源码 |
| git tree SHA 不含来源身份：不同仓库的相同子树哈希相同；本方复制管线（symlink 解引用、目录过滤）也会改变树哈希 | 实测（哈希实验） |
| v2.102.0 无 dismiss 写锁路径 | 源码（未找到） |

既有约束：AGENTS.md 文件系统唯一真相 / 最小总复杂度；Local Protocol Guardrails（docs + fixtures + 双端测试同 change）；`~/.agents/` 不放应用私有文件。

## Goals / Non-Goals

**Goals:**

- 外部正常重写路径下，本方更新基线存活；不再静默掩盖待更新。
- 本方读写对未声明字段零新增损失（双端）。
- 缺失/冲突/不完整溯源一律显式状态，不静默择一、不静默吞掉。
- 外部 pin 不被本方破坏。

**Non-Goals:**

- 来源归属（同名接管）检测与恢复——对象模型上内容哈希证明不了身份（上表末行），且无独立记录无法区分剥离与接管。**收缩为二期选项（B 方向），触发条件见 watch 清单。** 本期 spec 不承诺。
- 恢复已丢失的显式 `ref`（信息已不存在，接受丢失 + 文档化回落）。
- pin 安装 UX、publish/search/校验器、SSOT 布局与安装管线变更、Codex 路径迁移。

## Decisions

### D1 基线载体：写入共享 schema 的 `skillFolderHash`，`commitSha` 降为兼容镜像（四案记录）

| 案 | 内容 | 裁决 | 理由 |
|---|---|---|---|
| E 原语 | 本地计算 git tree SHA 判归属/自愈 | **否决** | 树哈希不含来源身份（identity-blind，实测同内容跨仓同哈希）；本方复制管线自身改变哈希 → 自身认证也不成立；保真度矩阵（模式位/Unicode/大小写/转换）是无底洞 |
| A 全量 | skillFolderHash 载体 + E 原语 | **否决** | 依赖被否决的 E |
| B sidecar | 私有账本承载基线+归属 | **二期，watch 触发** | 满足全部四项不变量，但引入并行账本：每条内容生命周期（安装/更新/删除/归档/恢复 × 双端）都要维护，三方失败语义与迁移信任边界成本随功能复利；第一轮评审在其现状形态上否决，补全属独立立项 |
| **A′** | **skillFolderHash 权威 + commitSha 镜像 + 显式状态** | **采纳** | 载体在 gh 重写下存活（实测）、vercel 消费同语义值（互操作收益）、值语义由 git 定义；无新文件、无并行生命周期、无版本 bump、无第二真相 |

- 读序：`skillFolderHash` 有值 → 权威；缺失 → `commitSha` 回落；两字段皆有且值不同 → 显式冲突；皆缺 → 无基线（显式 needs-re-confirmation）。
- 写序：安装/更新同时写两字段（镜像保旧版可读与降级安全——旧版结构体已声明 `skillFolderHash`，其重写不会剥它）。
- 前提的验证边界：已验证「正常 v3 重写路径」；`readFrom` 对损坏/未来版本文件返回空导致整表重置属上游风险，本方不可防，靠 watch + 上游 issue（D5）。
- 诚实边界：基线是「远端快照引用」，不承诺安装字节与该 tree 逐字节一致（可移动 ref 在下载与取树之间漂移的既有窗口，本期不变亦不恶化）。

### D2 未声明字段无损往返：类型化 `pinnedRef` + `#[serde(flatten)]`

`SkillLockEntry` 增加显式 `pinnedRef`（pin 闸门需要类型化识别），其余未声明键经 flatten 原样往返；顶层 `SkillLock` 同样加 flatten——否则本方会对 vercel 未来新增的顶层键成为新的有损写入者，与本 change 立场自相矛盾。备选「逐字段跟随上游枚举」否决：每次上游加字段都要追平，flatten 一次到位。

### D3 更新检查语义改造

- 基线按 D1 读序取值；`has_update` 仅在有基线且无冲突时比较。
- **检查绝不回写基线（E1 评审修订）**：`check_skill_updates` 只呈现状态，不写锁。基线只由安装/更新流程按实际落盘内容建立，或按 docs 的外部修复配方修复。
- **为什么检查不回写**：检查先读锁快照、联网、再写回；写回时既无法证明本地内容仍等于远端 tip（「安装于 48h 内」只是时间推测），也不复核当前条目是否已被并发写入（外部工具在本方 await 期间写入的冲突/新基线会被静默覆盖，实测竞态）。代价是安装时树查询失败的降级条目需重装或配方修复才能恢复检查，换取检查不掩盖、不覆盖并发状态。
- 批量/单技能更新的 commitSha 相等门改为按同一读序取基线比较；冲突条目拒绝更新并显式报因。
- 含 `pinnedRef` 条目在候选筛选阶段跳过，显式状态。
- 新状态经既有 IPC 类型面下发，前端沿用既有更新状态展示模式渲染，不新增能力面。

### D4 fixtures 与双端测试

新增 fixtures：gh 形态往返样例（含 `pinnedRef`、未知键、仅 `skillFolderHash` 的条目）、双载体冲突样例、pin 条目样例；Rust/CLI 协议测试消费同一组 fixtures。

### D5 上游 issue（并行，不阻塞）

向 cli/cli 报两个事实：① 锁重写对未声明字段有损往返（`ref`/`commitSha` 类扩展字段丢失）；② `readFrom` 对不认识/损坏文件返回空状态 → 写回可能整表重置。附 evidence/ 探针。上游修复后可简化镜像，但不改读序语义。

## Risks / Trade-offs

- [上游改变 `skillFolderHash` 语义或开始剥它] → 读序逐级降级（commitSha → 显式状态），坏一点不坏掉；watch 触发器重跑探针。
- [同名接管不可见]（明确接受的缩水）→ 低频且非自伪装（技能内容变化可被用户察觉）；watch：真实用户报告 → B 二期立项，A′ 不预判不阻塞。
- [安装时树查询失败的降级条目不自愈] → 状态显式挂起，重装或按 docs 配方修复即恢复；换取检查不掩盖、不覆盖并发状态。
- [历史已剥离条目升级后浮出显式状态] → 暴露既有伤害而非新增；状态持续保留（不自愈），release notes 提供 AI 修复配方。
- [检查只读使长期缺基线技能需人工修复] → 显式 needs-re-confirmation + release notes 配方；接受为正确性优先的代价。
- [flatten 保留畸形未知键] → 「无损」的固有代价；fixtures 覆盖值语义校验。
- [旧版本桌面重写条目丢 `pinnedRef`] → 旧版不认识该字段；升级后双端即无损；文档记录此单向损耗。

## Migration Plan

1. 无强制迁移：读序回落覆盖存量（有 `commitSha` 的条目照常工作）；下一次本方写路径顺带升级为双字段。
2. 回滚边界（如实限定）：旧版可读且保留 `skillFolderHash`（其结构体已声明该字段），但旧版的更新路径只写 `commitSha`——回滚后若用旧版执行更新，会产生双载体冲突，由本方案的显式冲突状态接住（可读、可诊断、需用户决策），而非静默不一致。`pinnedRef` 与未知字段在旧版重写时会丢失（单向损耗，升级后即恢复双端无损）。
