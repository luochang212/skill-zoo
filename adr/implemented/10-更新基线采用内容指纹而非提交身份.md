# ADR: 10 更新基线采用内容指纹而非提交身份

## Problem

根级 skill（skillPath 为空）的更新检查永远误报。机制：`fetch_repo_tree`（src-tauri/src/services/cli.rs:533-545）向 GitHub 传分支名或 commit sha，而 GitHub Trees API 响应的 `.sha` 字段**回显解析后的 commit sha**，不是根 tree sha（实测：传 `main` → 回显 HEAD commit sha；2026-11-12 实验，见 `_reversa_sdd/experiments/update-baseline-experiment.md`）。`get_folder_sha_from_tree`（cli.rs:573-578）对空路径返回该回显值，于是根 skill 的"基线 vs 最新"实为"安装时 commit sha vs 当前 HEAD commit sha"（cli.rs:397 比较）——安装后任何一次提交都触发"有更新"，包括 `--allow-empty` 空提交。子目录 skill 不受影响：比较对象是递归列表中的目录 tree 条目 sha，是真内容指纹。

该缺陷在仓库中不可通过读代码发现：回显行为只存在于 GitHub 侧。同类工具 vercel-labs/skills 的根级兜底 `return tree.sha`（src/blob.ts:302）踩同一个坑，证明这不是本仓库独有的设计失误，而是 API 陷阱。

## Decision

lock 条目新增可选字段 **`contentDigest`**（string，sha256 hex，64 字符小写）：对该 skill 在远端递归树中路径前缀下**全部条目**（blob 与 tree）按 `path \0 sha \n` 逐行拼接、按 **UTF-8 字节序**排序后求 sha256。

- 安装（`update_lock_after_install`）与更新成功（`reinstall_skill_from_discovered`）时写入 `contentDigest`，与 `commitSha` 并行
- 更新检查（`known_update_from_tree`）：双方都有 `contentDigest` 时以指纹相等决定"无更新"；任一侧缺失时回退现有 commitSha 比较（存量基线自然迁移：旧条目保持旧行为，第一次真实更新后即获得指纹）
- `KnownSkillUpdate.latest_sha` 与重装前校验（`actual_sha == latest_sha`，cli.rs:1043）保持树 sha 语义不变——指纹只决定"要不要更新"，不参与重装一致性守卫
- 本地漂移基线 `skillFolderHash`（lock.rs:139-149 的本地内容哈希，服务 merge guard）**不动**：远端指纹与本地漂移基线是两条独立的线
- 批量路径对"缺基线"的静默跳过（cli.rs:303-315 的 `report_missing_baseline = to_update.len() == 1`）改为与单 skill 路径对称的显式报错
- CLI 侧不实现指纹计算（CLI 无更新命令）；协议遵从靠既有"未知字段保留"与 fixture 测试
- 排序语义按 UTF-8 字节序：Node 与 Rust 的默认排序在多字节路径上不同，双实现（若未来 CLI 引入指纹）必须以字节序对齐；测试向量必须含多字节路径（实验已验证 Node `Buffer.compare` 与 Rust `Vec<u8>` sort 逐字节一致）

## Alternatives considered

- **沿用 tree.sha、只在根路径特判**：根路径没有独立于提交的 tree sha 可取，此路不通——这正是缺陷的根源。
- **vercel 式重 clone 内容哈希**（对 fresh clone 重算 `hashSkillFiles` 式内容哈希，vercel-labs/skills 项目级更新即此路）：正确但每次检查都要下载，成本不可接受；我们已有零下载的 tree 数据可用。其思想（内容寻址、UTF-8 字节序、排除安装器不写的内容）已吸收进指纹定义。
- **统一本地 `skillFolderHash` 与远端基线为一种哈希**：本地哈希吃文件内容、远端只有 blob sha，原料不同无法统一；且统一会触发协议门控、使全部存量漂移基线失效。两条线分工（远端指纹管"远端变没变"，本地哈希管"本地动没动"）成本为零且语义清晰。
- **lock 版本 bump**：`contentDigest` 是可选新增字段，协议"未知字段保留、拒绝未来版本"的既有规则保证旧读取方兼容，bump 会无谓地把所有旧 lock 判为不可写。

## Consequences

### Verification

- 新装与更新后的根级 skill，lock 中同时有 `commitSha` 与 `contentDigest`
- 根级 skill 在远端**空提交**后不再报"有更新"（单测：同 tree、不同 commit 的两个树响应，指纹相等）
- 子目录 skill 行为不变（既有测试全绿）
- 无 `contentDigest` 的存量条目走 commitSha 回退路径，有明确测试覆盖
- 指纹纯函数的单测含多字节路径向量，断言与独立实现（实验脚本的 Node 侧）输出逐字节一致
- `fixtures/local-protocol/` 的 lock fixture 含 `contentDigest` 示例，CLI 协议测试验证读-写-读保留该字段
- 批量更新对缺基线 skill 报错而非静默跳过
- `docs/local-protocol.md` 的 lock 字段表收录 `contentDigest` 及其算法一句话定义

### Trade-offs

- **迁移期噪音**：存量根 skill 第一次检查仍走 commitSha 回退（照旧误报），用户更新一次后才精确。已知且可接受，不为此引入自动迁移。
- **树截断**：`truncated=true` 的超大仓库指纹不完整。现有代码路径（tree sha 比较）有同样的盲区，指纹不使其恶化；不为不可能发生的规模写处理。
- **GitHub 响应契约漂移**：指纹依赖"递归树条目的 path/sha 稳定"，这是 git 数据模型（blob/tree sha 内容寻址）而非 API 行为，回显陷阱不再涉及。
- **双实现排序分叉**：CLI 未来若实现指纹计算，必须复现 UTF-8 字节序与多字节向量——已在 Proposal 中钉死，fixture 测试是护栏。
